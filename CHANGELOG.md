- **Publishing no longer reports a previous run's verdict as this one's.** `lastFinishedPublishOperation` is the *last finished* operation and publishing is asynchronous, so reading it straight after publishing returns the earlier attempt's result. Caught live: a publish reported "FAILED" citing a component that had **already been deleted**, because the record belonged to a previous run. `publish_copilot_agent` now captures the prior operation's end time before publishing and, when the record has not moved, says the result is not in yet instead of describing the wrong run. It also names the specific degraded state behind that: an agent can sit in **`Synchronizing`** after a failed publish, accepting further publishes (HTTP 200) without ever recording an outcome — observed live for roughly twelve hours — so the tool says "stuck mid-sync, open it in Copilot Studio" rather than telling you to keep waiting.
- **Knowledge-source kinds are now checked.** An unrecognised `source.kind` fails publish with the singularly unhelpful *"Node is unknown to the system"* — no component named, no property named. `validate_copilot_agent` and the write tools now flag a kind outside the set that is known to work. `SharePointSearchSource` and `PublicSiteSearchSource` were both confirmed by publishing an agent with each; `GraphConnectorSearchSource` is documented but untested here, so it is allowed rather than flagged.

- **`audit_copilot_agent_access` (241 tools) — who can actually talk to your agents.** Agents carry three security settings that decide reachability: `authenticationmode` (No authentication / Integrated Entra / Custom Entra / Generic OAuth2), `accesscontrolpolicy` (Anyone / Agent readers / Group membership / Anyone including outside the tenant) and the authorized security groups. The tool reports them per agent — one agent or a sweep of everything you can see — and flags the combinations that expose one. The headline case is not hypothetical: a **published agent with `authenticationmode: No authentication` handed a conversation token to a plain unauthenticated GET**, so anyone who could reach its endpoint could chat with it. The same setting on an unpublished agent is noted rather than flagged, because there is no runtime to reach. It closes by saying plainly that Dataverse row security means agents owned by other people are invisible, so this is not a tenant-wide audit.

- **All eight of Copilot Studio's undocumented bound actions were tested, and the verdicts are recorded in the code.** `PvaPublish`, `PvaDeleteBot` and `PvaGetDirectLineEndpoint` are used by these tools. The other five are deliberately not, and the reasons are written down so nobody repeats the work: `PvaAuthorize` returned 204 from an unshare and revoked nothing; `PvaCreateBotComponents` works only when every component carries `parentbotid@odata.bind` (without it, 204 and nothing created) and returns no ids, so individual creates — same result, per-component feedback, no silent-failure mode — are preferred; `PvaPublishStatus` wants a job id nothing in the Dataverse surface produces (`PvaPublish`'s own job field comes back null); `PvaProvision` is a no-op on an already-provisioned agent; `PvaCreateContentSnapshot` returns `SnapshotId: null` with no observable artifact. Also found: `PvaDeleteBot` requires OWNERSHIP — a user the agent was merely shared with, even read/write, gets HTTP 400.

- **`chat_with_copilot_agent` (240 tools) — you can now TEST an agent, not just inspect it.** Send a message and get the agent's replies back, which closes the loop: an agent created, authored and published entirely through these tools then answered a real message. It needs the agent PUBLISHED and a Copilot Studio licence on the signed-in user. Two behaviours worth knowing: each call starts a fresh conversation (a cold start, not a continuing thread), and Direct Line **echoes your own message back without preserving the sender id you set** — filtering by sender alone reports the user's own words as the agent's first reply, so the sent activity is excluded by id. The conversation token is a credential, so the endpoint host Dataverse returns is checked against the Microsoft gateway domains before anything is sent to it, and a non-HTTPS endpoint is refused.

- **`get_copilot_agent_endpoint` (239 tools) and a delete that uses the platform's own action.** Scraping the Dataverse metadata surfaced eight bound actions on `bot` that Microsoft does not document: `PvaPublish`, `PvaDeleteBot`, `PvaGetDirectLineEndpoint`, `PvaAuthorize`, `PvaProvision`, `PvaPublishStatus`, `PvaCreateBotComponents`, `PvaCreateContentSnapshot`. Two are now used. `get_copilot_agent_endpoint` returns the agent's Direct Line endpoint — the address a chat client uses to actually converse with it (proven end to end: an agent created, authored and published entirely through these tools then answered a real Direct Line message). It needs a Copilot Studio licence on the signed-in user; an unlicensed account is refused with "User Viral license is expired". And `delete_copilot_agent` now calls `PvaDeleteBot`, which cascades to every component in one call (verified: an agent with 15 components left nothing behind), falling back to the component-by-component order if that action is unavailable.
- **`PvaAuthorize` is deliberately NOT used for sharing.** It looks like the native share action, but an unshare call returned HTTP 204 and revoked nothing — the recipient still saw the agent and all 18 components. Its role-type semantics are undocumented and a share tool that silently fails to revoke is worse than none, so sharing continues to use explicit `GrantAccess` grants, which are verified to work.

- **`validate_copilot_agent` also checks the flow references that break publishes.** A topic that invokes a cloud flow the environment cannot resolve fails the ENTIRE publish with `NotFound: CloudFlow … not found`, and nothing surfaces it until you publish. The validator now extracts every `flowId` from an agent's topics and checks each one, naming the topic that uses it. It deliberately reports "present in Dataverse" rather than "resolvable": a workflow row can exist while the Power Automate service does not serve the flow, and publish still rejects that — verified live, so claiming more than was checked would send people hunting in the wrong place.
- **Honest about what cannot be checked.** Dataverse stores component content as an opaque string and validates none of it, so a malformed topic saves happily and only fails in the designer or at publish. `validate_copilot_agent` lints what is checkable outside Copilot Studio (missing/incorrect `kind:` headers, empty content, tabs in YAML, missing instructions) and says plainly that it is not a full validation. The write tools carry the same caveat rather than implying a save means valid.

- **Security — the bundled `qs` floor is raised to 6.16.0 (two medium-severity advisories, Snyk priority 524).** `qs` reaches this package transitively through `@modelcontextprotocol/sdk` → `express`/`body-parser`. 6.15.2 is vulnerable to an uncaught exception in `stringify()` when a crafted query string plants a non-callable `constructor.isBuffer` (SNYK-JS-QS-19432019, CWE-248 — can kill a worker process) and to unbounded array allocation through the bracket-key comma form bypassing `arrayLimit` (SNYK-JS-QS-19432017, CWE-770). Both require qs parse options this server does not set, so this is exposure-closing rather than an active hole; the override floor moves from `^6.15.2` to `^6.16.0` so the patched build is actually locked in. `npm audit`: 0 vulnerabilities.

## [1.0.11] - 2026-08-29

- **Security — the bundled `fast-uri` floor is raised to 3.1.6 (three high-severity advisories).** `fast-uri` reaches this package transitively through `@modelcontextprotocol/sdk` → `ajv`, and 3.1.5 is affected by three high-severity URI-parsing flaws: double decoding of percent-encoded hostnames (CWE-174), improper handling of encoded scheme delimiters (CWE-177), and silent rewriting of malformed bracketed IPv6 literals into different valid addresses (CWE-1286). Each lets a crafted URI normalise or resolve to a host other than the one it appears to name, which can defeat SSRF checks, redirect validation, and host allowlists in anything that trusts the normalised result. An `overrides` floor was already in place but pinned at `^3.1.4`, which still resolved to the vulnerable 3.1.5 — raising it to `^3.1.6` is what actually moves it, and 3.1.6 remains inside ajv's own `^3.0.1` range so no dependency constraint is forced. `package.json` ships in the published tarball, so a fresh install resolves the patched version. A build-only `nanoid` override (`^3.3.18`, GHSA-2v37-7h3g-55p8) was added in the same pass; it arrives via `tsup` → `postcss` and never reaches an installed server. `npm audit` reports 0 vulnerabilities.

- **Bug fix — SharePoint/OneDrive tools no longer reject every real drive id.** Graph drive ids are `b!` + base64url (e.g. `b!NVXWgAg3TEO7IEtW…`), but the shared Graph-id validator's character class omitted `!` — so `upload_sharepoint_file`, `list_sharepoint_files`, and every other drive-scoped tool refused the very ids that `list_sharepoint_lists`/Graph hand back, with *"Invalid drive ID format: contains disallowed characters"*. Field report: uploading an Office Script `.osts` into a drive resolved minutes earlier by this same server was impossible; the only workaround was routing the write through a flow. The validator now accepts `!` and `=` (base64 padding); injection posture is unchanged — path separators, quotes, and template characters are still rejected.
- **Bug fix — `get_action_schema` no longer renders connector parameters as "undefined".** Swagger allows an operation's parameters to be `$ref`s into the document's top-level `parameters` map, and allows a path-level `parameters` array that applies to every operation on the path — connector swaggers (Excel Online (Business) especially) lean on both. The schema tool passed them through raw, so operations like `GetTables`/`GetDrives` rendered every parameter as `• **undefined** - undefined`, leaving the tool unable to answer the one question it exists for. `$ref`s are now resolved, path-level parameters merged (operation-level wins on collision), and the renderer falls back through `schema.type` and `x-ms-summary` instead of printing undefined. Static **`enum` constraints are now displayed** — the same session lost an hour to `RunScriptProd`'s `ScriptParameters` being silently pinned to `[null]` outside the designer, a fact the swagger carried all along; the schema tool now surfaces it as `Allowed values: [null]`. Internal-visibility parameters are labeled `(internal)`.
- **Bug fix — `clone_flow` now delivers the stopped clone its description always promised.** The create API brings new flows up **Started**, and the tool never stopped the copy — so cloning a recurrence-triggered flow armed a live trigger the moment the clone existed. Field report: a clone of a 5-minute-recurrence flow executed real Jira/Entra calls within ~40 seconds of creation, in an environment believed isolated (the source flow calls production over HTTP). The clone is now stopped immediately after creation; if that stop fails, the result says so loudly — `state` reports the true state and a `warning` names the exposure — instead of claiming Stopped. The `updateConnections` parameter's description now spells out the exact value shape (`{ connectionName, id, source?, tier? }` keyed by the source flow's reference keys), which previously had to be discovered through two zod rejections.

## [1.0.10] - 2026-08-26

- **Bug fix — `update_flow` now declares the `$connections` workflow parameter when an update introduces the flow's first connector action.** A flow created with no connector actions declares only `$authentication`; updating it to add an `OpenApiConnection` action carried over the old parameters block unchanged, so the service rejected the save with `InvalidTemplate` — *"The workflow parameters '$connections' are not valid; they are not declared in the definition"* — and the only workaround was recreating the flow with the connector present from the start. Both write paths now ensure `$connections`/`$authentication` are declared whenever connection references are attached or the definition contains connector actions; user-declared parameters and existing values are preserved, and connector-free metadata updates are untouched.
- **Bug fix — a `source: "Invoker"` connection reference no longer fails as "Missing connection" when the connection exists.** An Invoker reference carries a *logical* `connectionName` (e.g. `shared_sharepointonline`), not a real connection id — passing it straight to the flows API failed `ConnectionAuthorizationFailed`, which was mapped to *"Missing sharepointonline connection. Create it at make.powerautomate.com…"* even with a healthy SharePoint connection sitting in the environment. `create_flow` and `update_flow` now resolve logical connection names (Invoker refs, and any connector-shaped `connectionName`) against the environment's actual connections before saving — preferring a `Connected` one — and report the substitution in the result. "Missing" is now only reported when no connection of that connector type exists at all. Resolution fails open: if connections can't be listed, the reference is sent as given and the API stays the arbiter.
- **Better error — connection failures now name the environment they checked and what exists there.** The generic *"Missing X connection. Create it…"* message actively misled when the real problem was an environment mismatch (connections created in `test`, tool pointed at `Default-…`). On `ConnectionAuthorizationFailed`, `create_flow`/`update_flow` now report the environment that was checked and list the connections that DO exist for that connector there (name, display name, status) — or state plainly that none exist and suggest the connection may live in a different environment. When the inventory can't be fetched, the previous message is kept unchanged.

- **New best-practice check — `validate_flow` now flags flows that use embedded (direct) connections instead of connection references (solution ALM).** When a flow's connection references carry `source: "Embedded"`, validation now emits a warning — *"N connections use an embedded (direct) connection instead of a connection reference: …"* — naming the connection keys, with a fix pointing at solution connection references. This surfaces the maker-portal / Solution Checker guidance (*"Flows in a solution should use connection references … so connections can be provided during import"*) that the tool did not report before: a flow could score clean yet not import cleanly into another environment, because an embedded connection is pinned to one environment's connection while a connection reference lets the binding be supplied at import time. A flow whose connections are all references now reports a passed check. Backward compatible — when no connection-reference data is available the check stays silent, so existing output is unchanged except where the data is present.

## [1.0.9] - 2026-08-16

- **Bug fix — an action whose `inputs` is an array is no longer stored as an object.** `typeof [] === "object"`, and the preprocessor that fixes expression-bearing payloads spreads its argument into an object literal — so a `Compose` holding a literal list came back as `{"0":"a","1":"b"}`. `create_flow` reported success and the flow then failed at runtime with *"the result of the evaluation of 'foreach' expression … is of type 'Object'. The result must be a valid array."* An array has no `body`/`parameters` to rewrite, so it now passes through untouched; `update_flow`'s deep merge already guarded this, which is why only newly created flows were affected.

- **Bug fix — a destructive tool called without `confirm: true` reported SUCCESS while doing nothing.** The confirmation prompt was *returned* as ordinary text, so a refusal was indistinguishable from a completed delete: the MCP result carried no `isError`, and a script that deleted 59 SharePoint items and checked only that flag reported 59 deletions and performed none. All 36 refusals across 15 tools now raise a `ConfirmationRequiredError`, rendered verbatim so the prompt keeps the id you must confirm against. The interactive flow is unchanged — read the prompt, call again with `confirm: true`. `delete_flow` and `delete_custom_connector` also had their best-effort name lookup restructured so the prompt names the flow or connector instead of falling back to the id.

- **Bug fix — `get_flow` now tells you which connection a flow is bound to.** A flow's connection reference carries three easily-conflated things: the reference key (`shared_jira`), the connector type, and the actual bound connection id (`connectionName`). Only the first two were reported, so "which connection is this trigger using?" could not be answered from the tool. `connectionName` (and `source`) now appear in both the structured output and the summary, which also makes read → rebind a round trip since it is exactly the field `update_flow` accepts back.

- **Bug fix — the npm page pointed at the wrong repository.** `homepage`, `bugs` and `repository` all referenced `powerplatform-mcp-docs`, which is the *other* package's public repo — inherited when this package was forked from `powerautomate-mcp` 0.16.2. Anyone clicking Repository or Issues on the npm listing landed in the wrong project, and bug reports would have arrived on the wrong tracker. They now point at `powerplatform-mcp-server`. npm only refreshes this metadata on publish, so the listing corrects itself with this release.

## [1.0.8] - 2026-08-12

- **Bug fix — `create_connection` no longer produces connections that can never be signed in.** The create body always sent `connectionParameters` and never `connectionParameterSets`, so for a connector publishing more than one authentication mode the service stored a connection with *no* auth mode attached. It looked fine — the tool reported "Connection created" and handed over sign-in instructions — but the portal's *Fix connection* then showed only the parameter form with an **Update** button and no consent step, so reconnecting looped forever. Field report: an Azure Key Vault connection created this way sat `Unauthenticated` through repeated reconnect attempts and had to be deleted and rebuilt by hand. Azure Key Vault, SQL Server and Azure Blob all publish parameter sets, so this was the general case rather than one connector's quirk. `create_connection` now takes `parameterSet`, sends the correct `connectionParameterSets` shape, auto-selects when a connector publishes exactly one mode, and refuses up front — naming the valid modes — rather than creating a dead connection. Connector metadata that can't be read is not treated as an error: those connectors fall back to the previous behaviour, so discovery can never become a new way for a working create to fail.
- **Bug fix — `list_connections` ignored the `environment` argument.** The tool validated `environment`, logged it, then called `listConnections()` with no argument, so the API always filtered on its own configured environment. Connections are environment-scoped, so the result was a confident answer about the wrong environment. Field report: `list_connections({environment: <production>})` returned the DEFAULT environment's 82 connections — which read as "Jira is already connected in Production" when Production had none, and a flow migration was planned on the strength of it. The environment now reaches the API call and is validated like any other environment id; omitting it still uses the configured default. `build_flow` takes no environment parameter and is unaffected.
- **Bug fix — `validate_flow` no longer reports "Unbalanced brackets" on valid index accessors.** The pattern that finds bare `@function()` expressions ended in a greedy `.*\)`, which backtracks to the LAST `)` in the string — so anything closing after it was cut off. `@variables('EinToCompany')?[outputs('Parse_EIN')]` was captured as `variables('EinToCompany')?[outputs('Parse_EIN')` and then confidently reported as *"Unbalanced brackets: missing ']'"* on a flow that was valid and already deployed. A truncated capture is worse than none: it becomes a definite error about correct code. Expressions are now located by regex and terminated by a scanner that tracks paren/bracket depth, respects `''` escapes inside string literals, and follows chained accessors (`?['a']`, `.value`, `[0]`) to the real end. Genuinely unbalanced expressions are still reported.
- **Bug fix — a misspelled parameter no longer reports success while doing nothing.** Tool inputs are validated with zod, which *strips* keys it doesn't recognize rather than rejecting them — so a parameter named slightly wrong was silently discarded and the tool cheerfully reported that it had done the work. Field report: `update_flow` was called with `patchTrigger` (the real name is `trigger`, and `patchActions` next to it makes the wrong name look right), the tool answered *"Updated …"*, and the flow's trigger was never touched; the mistake only surfaced later when the schedule hadn't changed. Unknown top-level parameters are now rejected with an error that names the likely intended parameter (`'patchTrigger' (did you mean 'trigger'?)`) and lists the valid ones. Checked against each tool's published JSON Schema, so it needs no per-tool upkeep; nested objects — `fields`, `data`, a flow's `trigger` and `actions` — stay deliberately open-ended and are not policed.
- **Bug fix — `get_run_actions` now surfaces the real error on failed actions.** The platform's run-action records carry an `error` object for *skipped* actions (the runAfter noise) but leave it null for many genuine connector failures — so the one action that actually failed reported `error: null` while the AI had to dig the real 400 out of the raw outputs. Failed actions with no platform error now derive one from the already-fetched outputs (`[HTTP 400] …the vendor's actual message…`), platform-provided errors are untouched, and the summary line now counts skipped actions separately.
- **Bug fix — connector actions that take an object parameter save again.** Some connector operations declare a parameter as an object rather than a string — Files.com's *Move File or Folder* takes a `{ destination }` body, for example. When such a parameter contained an expression, the rewrite that keeps expressions out of object payloads emitted string interpolation (`@{json(...)}`), whose result is a String. Power Automate type-checks connector parameters against the connector's definition when the flow is saved, so it refused the flow outright: *"Input parameter 'body' validation failed … type/format 'String' is not convertible to type/format 'Object'."* Connector parameters now use the bare `@json(...)` form, which keeps the declared object type while still being the single expression that avoids object-level evaluation at save time. HTTP action bodies are untouched, and the runtime JSON-escaping of every substituted value is unchanged.
